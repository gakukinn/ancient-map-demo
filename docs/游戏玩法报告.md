# 帝国地图战争：游戏性与系统分析报告

## 1. 概述
当前版本是一个基于地理地图的实时历史战略游戏。核心循环包括时间推进（季节/年份）、实体移动（玩家/军团）以及由历史事件系统驱动的战斗遭遇（攻城/野战）。

**当前状态**：机制上可玩，功能正常，但在某些逻辑上依赖“硬编码”的启发式方法，并且存在混合系统（旧版与新版共存），这构成了长期的稳定性风险。

---

## 2. 基础运行与稳定性
**状态**：**稳定但存在风险**

### ✅ 运行良好
- **核心循环**：`GameApp.ts` 可靠地管理生命周期和时间更新。
- **渲染**：`Army`/`Legion` 逻辑与 `LegionRenderer` 之间的映射似乎已充分解耦，防止渲染崩溃影响逻辑。
- **数据完整性**：`FactionManager` 和 `CityManager` 正确处理静态数据加载。

### ⚠️ 稳定性风险
1.  **事件 ID 冲突 Bug (严重)**：
    -   在 `HistoricalEventManager.ts` 中，已处理的事件通过 `${year}_${season}_${type}` 进行追踪。
    -   **后果**：如果在同一季节发生两个相同类型的不同历史事件（例如，不同区域同时发生两场攻城战），第二个事件将被**静默忽略**。
    -   **修复**：在追踪键中包含唯一的事件索引或 ID。

2.  **混合战斗系统**：
    -   `SiegeManager` 使用 `CombatSystem.startRegionalBattle`（新的 `BattleField` 类）。
    -   `FieldBattleManager` 在默认情况下使用 `CombatSystem.startBattle`（旧版 `Battle` 类），但在某些情况下使用 `MultiLegionFieldBattle`。
    -   **风险**：野战与攻城战之间的行为（治疗、撤退逻辑、持续时间）不一致。

3.  **逻辑中的魔法数字**：
    -   距离检查散落在各处，使用任意值（自动加入用 `9999`，到达用 `< 0.5`，参战用 `< 1.5`）。
    -   **风险**：单位在目标附近“抖动”或未能加入视觉上重叠的战斗等边缘情况。

---

## 3. 逻辑合理性
**状态**：**尚可但需要统一**

### ✅ 合理的设计
-   **军队复用**：系统尝试寻找现有的“空闲”军队来执行事件，而不是生成无限的克隆体。这创造了一种持久感。
-   **季节性补给**：简单有效的节奏控制机制。

### ⚠️ 逻辑缺陷
1.  **玩家参战逻辑重复**：
    -   `SiegeManager` 和 `FieldBattleManager` 都实现了自己的“玩家自动加入”逻辑 (`checkPlayerParticipation`)。
    -   **问题**：对其中一个的更新（例如添加“撤退”选项）不会应用到另一个。
    -   **建议**：将此逻辑移动到 `Player.ts` 或 `CombatSystem.ts`。

2.  **递归的“链式”逻辑**：
    -   `SiegeManager` 中的 `processAfterBattleChain` 处理多阶段战役。它依赖于嵌套的回调。
    -   **问题**：如果链条断裂（例如单位在链条中间被销毁），很难调试。

3.  **经济绕过**：
    -   即使阵营破产，事件也会强制征兵（`recruitedTroops < 1000` 覆盖现实）。
    -   **结论**：这对于“历史”流程是必要的，但如果玩家试图通过经济战获胜，这会破坏“策略性”。

---

## 4. 游戏平衡
**状态**：**确定性且偏向街机风格**

### 观察
-   **战斗**：使用确定性模型（类似兰彻斯特方程）。
    -   持续时间由比例固定（30秒 到 7.5秒）。
    -   赢家损失由比例计算（50% 到 5%）。
    -   **优点**：节奏可预测。
    -   **缺点**：缺乏以少胜多的“英雄”时刻（侧翼包抄纯粹是视觉效果）。

-   **兵力限制**：
    -   野战上限为 10,000 兵力。
    -   这简化了性能，但对于“史诗”战争来说可能感觉规模较小。

---

## 5. 建议（最小化干预）

为了达成“基础优先，不添加新功能”的目标，我建议进行以下严格的修复：

1.  **修复事件冲突**：更改事件追踪键，防止跳过事件。
2.  **统一常量**：将所有距离“魔法数字”移动到 `GameConfig.ts`，以确保交互范围一致。
3.  **标准化战斗**：确保野战也尽可能使用 `BattleField`（区域）系统，或者至少确保“撤退”逻辑一致。
4.  **无新内容**：不添加新单位、机制或阵营。

**立即执行的下一步**：
- 修复 `HistoricalEventManager` 中的 Bug。
- 修复重复的“撤退”逻辑（确保玩家战败后能正确撤退）。
