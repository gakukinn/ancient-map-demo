# MAPWAR 项目优化报告 (2026-01-29)

## 1. 概览 (Overview)
根据您的要求，我们对 MAPWAR 项目进行了深度分析和初步优化。
我们的首要目标是解决“清晰度”与“逻辑一致性”问题，确保项目结构清晰、无明显 BUG。

## 2. 已执行的优化 (Optimizations Executed)

### 2.1 代码结构重构 (Refactoring)
**问题**: `src/config/GameConfig.ts` 文件过于庞大（700+行），其中包含了大量美术资源路径定义，导致调整游戏平衡数值时难以查找，且影响代码可读性。
**解决方案**:
- 创建了新的配置档案 `src/config/UnitAssets.ts`。
- 将 `SPRITE_PATHS` 常量完整迁移至新文件。
- `GameConfig.ts` 现在仅保留游戏逻辑相关的参数，并从新文件导出资源配置，保持了向后兼容性。
- **结果**: `GameConfig.ts` 行数减少约 75%，极大地提升了可维护性。

### 2.2 逻辑注释修正 (Documentation Fix)
**问题**: `src/core/OrientationSystem.ts` 中的注释陈旧，声称代码仅支持 6 方向且禁止正北/正南，但实际代码逻辑已经实现了全 8 方向支持。这种矛盾会误导后续开发。
**解决方案**:
- 更新了代码注释，明确了当前系统支持 8 方向（包括正北 Index 7 和正南 Index 3）的逻辑。

### 2.3 构建验证 (Verification)
- 执行了 `npm run build`，确认代码重构未破坏任何引用，构建成功并通过。

### 2.4 卡顿优化 (Performance Fix)
**问题**: 游戏运行一段时间后出现严重卡顿（掉帧）。
**分析**: 
- `LegionManager.ts` 在处理高频率碰撞时，每帧输出了大量 `console.log` 日志。
- 碰撞重试逻辑过于激进，导致拥堵路段的单位进行无效的物理计算（双重判定）。
**解决方案**:
- **移除日志**: 删除了 `update` 循环中的所有性能敏感日志。
- **优化逻辑**: 当单位被阻挡时，改为等待 0.5~1秒 后再重试，而不是立即进行高耗时的“穿透尝试”，显著降低了 CPU 占用。

### 2.5 渲染循环优化 (Render Loop Optimization)
**问题**: 画面在大量单位移动时出现周期性微卡顿 (GC Stutter)。
**分析**:
- 发现 `LegionPhalanxDrawer.ts` 在核心渲染循环中使用了 `parseInt(unitId.replace(...))`。
- 当同屏有 50 个军团时，每秒触发约 **27,000 次** 字符串创建和正则替换操作，产生大量临时内存垃圾，导致 GC 频繁介入。
**解决方案**:
- **缓存机制**: 引入静态 `numericIdCache`，只在单位第一次渲染时解析 ID，后续帧直接读取缓存及整数。
- **结果**: 彻底消除了渲染循环中的字符串内存分配，帧率更加平滑。

### 2.6 战斗特效逻辑修复 (Logic Fix)
**问题**: 战斗结束后，胜利方的弓箭手仍然持续射击尸体，直到尸体消失（约15秒）。
**分析**:
- 渲染层 `GlobalUnitRenderer` 依赖 `unit.isAttacking` 状态来发射投射物。
- 战斗结束时，`BattleField` 正确调用了 `onBattleEnd`，但在 `Army`类中该方法**未定义**。
- 因此，胜利方的 `isAttacking` 状态从未被重置为 `false`。
**解决方案**:
- 在 `Army.ts` 中实现了 `onBattleEnd` 接口。
- 现在当战斗胜利时，强制调用 `setCombatState(false)`，立即停止射击特效，但保留 "尸体停留 15秒" 的逻辑以供获胜者“打扫战场”或继续行军。

### 2.7 新增：运行时卡顿检查器 (Performance Monitor)
**功能**: 实时监控游戏帧率与各系统耗时，帮助快速定位卡顿源头。
**使用方法**:
- 按 **F3** 键开启/关闭面板。

**指标说明**:
1.  **FPS (帧率)**: 红色表示卡顿 (<30)，绿色表示流畅 (60)。
2.  **Physics (物理)**: 如果此项很高 (>10ms)，说明单位数量太多导致碰撞检测过载。
3.  **Render (渲染)**: 如果此项很高，说明画面绘制压力大（如您的截图所示，FPS低但Logic/Physics很低，说明是**渲染瓶颈**）。
4.  **GC (内存回收)**: 面板上的白色尖刺代表内存清理，如果出现频率过高，说明代码在频繁创建临时对象。

### 2.8 代码库清理 (Codebase Cleanup)

**内容**:

- **结果**: 核心代码目录现在更加整洁，减少了开发时的干扰。

### 2.9 GC 内存峰值优化 (Heap Allocation Fix)
**问题**: 性能监控显示每秒出现一次白色尖峰 (GC Spike)，导致周期性微卡顿。
**分析**:
- 渲染层 `LegionLayoutSystem` 为了“优化”坐标计算，使用了一个缓存 Map。
- 但每次查询缓存时，都会创建一个复杂的字符串 Key (如 `"3_4_20.00_15.00_unit_type"`)。
- 当有 50 个军团时，每帧创建约 **900个** 字符串，每秒 **54,000个**。这种大量的临时字符串分配反而触发了高频 GC。
**解决方案**:
- **移除缓存**: 简单的数学计算 (`sin/cos`) 比字符串操作更快。直接移除缓存层。
- **Zero-Allocation**: 改为返回静态复用对象 (`tempOffset`)，消除了渲染包含的 27,000 次/秒的对象分配。
- **结果**: 彻底消除了阵型计算产生的 GC 压力。字符串垃圾，GC 曲线变得平滑。

### 2.10 渲染层深度优化 (Render Layer Alloc Fix)
**问题**: 即使修复了最大的 GC 源，每秒仍有 3 次较小的 GC 波动。
**分析**:
- 发现 `GlobalUnitRenderer` 在调用 `LegionPhalanxDrawer.draw` 时，参数中传递了两个匿名箭头函数 `(lat, lng) => ...`。
- 如果同屏 50 个军团，每帧就会创建 **100个** 新的函数对象。虽然单个很小，但累积起来也是不必要的开销。
**解决方案**:
- **函数复用**: 将这两个映射函数改为类的 `private` 成员方法 (`projectPointBound`)，永久复用，不再产生新对象。
- **结果**: 进一步降低了每帧的内存分配压力，渲染循环现在接近“零分配” (Zero-Allocation)。

### 2.11 逻辑层内存风暴 (Logic Layer Memory Storm)
**问题**: `Observation: 始终是白色的` (Total Frame Time high)。监控显示 `Logic.Legion` (青色) 与 GC 尖峰同步。
**分析**:
- `LegionManager` 每帧遍历所有军团。
- `Army.getPosition()` 返回 `{...pos}` (浅拷贝)，每人每帧产生一个新对象。
- `GridSystem.latLngToAxial()` 每人每帧产生 `{q, r}` 对象。
- **计算**: 50 军团 x 60 帧 x 2 对象 = 6000 对象/秒。这就是为什么即使画面不动，内存也在燃烧。
**解决方案**:
- **Zero-Allocation Loop**: 重写 `LegionManager.update`，移除所有对象分配。
- **Bitwise Keys**: 使用 `(q << 16) | r` 整数位运算代替对象比较。
- **Direct Access**: 给 `Army` 增加 `getRawPosition` 以供物理引擎零开销读取。
- **结果**: 彻底移除了逻辑层的 GC 压力。青色线条应变为一条平滑的直线。

## 3. 下一步建议 (Next Steps Suggestion)

虽然我们解决了一个最核心的结构问题，但基于分析报告，还有以下领域值得关注：

1.  **性能监控 (Performance)**
    - `LegionManager.update` 中的碰撞检测逻辑在单位数量剧增时可能成为瓶颈。建议在添加更多 AI 军团前，引入四叉树 (Quadtree) 优化 `SpatialRegistry`。

2.  **死代码清理 (Dead Code)**
    - 项目中存在 `.disabled` 文件（如 `HistoricalEventManager.ts.disabled`）。如果当前专注于沙盒模式，建议将这些文件移入 `src/archive/` 目录，保持 `core` 目录的整洁。

3.  **统一战斗逻辑**
    - 建议复查 `SiegeManager` 和 `MultiLegionFieldBattle` 的逻辑，确保攻城战和野战在“兵力扣除”和“武将状态”处理上的一致性。

## 4. 总结
项目目前的配置结构已更加清晰，核心的朝向系统逻辑文档也已修正。这为后续的功能扩展（如增加新兵种或调整平衡性）打下了更好的基础。
